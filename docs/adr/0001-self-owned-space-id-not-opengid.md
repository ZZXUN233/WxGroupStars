# ADR-0001: 群空间用自建 spaceId 而非微信 openGId 作为业务主键

## 状态
已接受

## 背景
PRD 期望"绑定真实的微信群"。但微信小程序平台的群信息能力存在硬性限制：
- **群 ID**：仅能通过 `shareTicket`（群聊中分享）/`getShareInfo` 解密得到 `openGId`。
  它是"小程序 + 群"语境下的不稳定标识——不同小程序对同一群得到不同 openGId，
  openGId 无法逆推回真实微信群，不能作为稳定业务主键。
- **群名称**：微信无任何接口返回真实群名，只能由创建者在创建群空间时手动填写。
- **群成员列表**：微信不开放，只能维护小程序自建的成员关联表。
- **群主身份**：微信不开放——小程序**无法识别谁是群的"群主"**，也无法感知群主变更
  （仅能通过 shareTicket 解密得到 openGId，不包含任何成员/群主信息）。

因此"绑定真实微信群"在业务上不可行，只能以自建群空间实体近似。

## 决策
- 以**自建 `spaceId`** 作为群空间的业务主键，稳定、可控、可迁移。
- **`openGId` 仅作为辅助字段**：用于在"群聊中分享加入"时做**去重判断**，
  防止同一用户通过多个入口对同一群创建冗余，不承担业务主键职责。
- 群名称由创建者在创建流程中手动填写。

## 后果
- 优点：主键稳定，数据模型不依赖微信加密链路与 openGId 的不稳定语义；
  跨平台（若未来可能）也可复用自建 spaceId。
- 代价：无法真正识别"同一真实微信群"，同一微信群若从不同 Uniapp/小程序入口进入，
  可能映射为不同 spaceId（由 openGId 辅助去重尽量缓解）。
- 空间的管理者（owner）由产品自建：默认 = **创建者**，且**提供 owner 手动转让**（MVP 范围）——
  现任 owner 可将管理权转给本群任一成员（仅 owner 可发起、目标须为本空间成员；
  转让后原 owner 降为普通成员；MVP 无需目标二次确认）。微信无法识别真实群主（见背景），
  转让是覆盖"群换了群主"场景的切实路径。
